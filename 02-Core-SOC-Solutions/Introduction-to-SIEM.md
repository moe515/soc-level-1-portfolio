# Introduction to SIEM

**Path:** SOC Level 1 -> Core SOC Solutions
**Room:** Introduction to SIEM (https://tryhackme.com/room/introtosiem) - 120 min
**Status:** Completed

## Objective
Understand why logs alone aren't enough, what a SIEM (Security Information and Event Management) solution does, and how logs are collected, normalized, correlated, and turned into actionable alerts.

## Key Concepts

### 1. Log Sources: Host-Centric vs. Network-Centric
- **Host-centric logs** - generated by an individual device (Windows, Linux, servers): file access, authentication attempts, process execution, registry modifications, PowerShell execution.
- **Network-centric logs** - generated when hosts communicate with each other or the internet, from devices like firewalls, IDS/IPS, routers: SSH connections, FTP access, web traffic, VPN access, network file sharing.

### 2. Why Logs Alone Aren't Enough ("Answers Nowhere")
- **Numerous log sources** - hundreds of events per second across many devices, tedious to review individually.
- **No centralization** - would need to connect to each log source separately (SSH, RDP, etc.) to investigate, wasting time.
- **Limited context** - individual logs look harmless in isolation but tell a different story when correlated (e.g. a file access event combined with a lateral-movement login).
- **Limited analysis capacity** - manually reviewing huge log volumes is unrealistic for human analysts.
- **Format issues** - different log sources use different formats, making manual cross-referencing difficult.

### 3. What a SIEM Solves
A SIEM centralizes log collection, standardizes format, correlates events across sources, and detects malicious activity using detection rules - solving the exact problems above.

### 4. Core SIEM Features
- **Centralized log collection** - pulls logs from all sources (endpoints, servers, firewalls) into one place via lightweight agents or APIs.
- **Normalization** - breaks raw logs (which vary by OS/device) into consistent fields (parsing), so all sources can be compared side by side.
- **Correlation** - links individually-harmless events across sources into a single suspicious pattern (e.g. VPN login from a new IP + accessing shared docs + running PowerShell + outbound connection = potential data exfiltration).
- **Real-time alerting** - detection rules (built-in or custom) trigger alerts automatically when conditions are met.
- **Dashboards and reporting** - summarized, actionable views: alert highlights, system notifications, failed login attempts, events ingested count, rules triggered, top domains visited.

### 5. Log Sources and Ingestion
- Windows logs are reviewed via Event Viewer; Linux logs live under paths like /var/log/httpd (web), /var/log/auth.log (authentication), /var/log/cron (scheduled jobs); web servers generate access logs (e.g. Apache logs) recording every request.
- **Ingestion methods:**
  - Agent/Forwarder - lightweight tool installed on the endpoint that collects and sends logs to the SIEM.
  - Syslog - widely supported protocol for pushing logs from various systems (routers, servers) directly to the SIEM.
  - Manual upload - some solutions allow manually uploading log files for quick analysis.
  - Port forwarding - configuring endpoints to send data to a specific port on the SIEM listening for it.

### 6. Detection Rules and Alerting
Detection rules are logical expressions that trigger alerts, e.g.:
- 5 failed login attempts within 10 seconds -> "Multiple Failed Login Attempts"
- Successful login right after multiple failures -> "Successful Login After Multiple Login Attempts"
- USB plugged in (if restricted by policy) -> alert
- Outbound traffic over a size threshold -> potential data exfiltration alert

Rules are typically built from a log source + specific Event ID + a matching field value (e.g. WinEventLog + EventID 4688 + NewProcessName contains a suspicious string). Normalized logs are what make these field-based rules possible.

### 7. Alert Investigation Workflow
Once a rule triggers, the analyst reviews the dashboard, examines the underlying events/flows, and determines a verdict:
- **False Positive** - may require tuning the rule to prevent recurrence.
- **True Positive** - investigate further, contact the asset owner, isolate the infected host, block the malicious IP as needed.

## Skills Gained

- Distinguishing host-centric vs. network-centric log sources
- Explaining the limitations of analyzing logs without a SIEM
- Understanding core SIEM capabilities: collection, normalization, correlation, alerting, dashboards
- Knowing common log locations and ingestion methods (agent, syslog, manual upload, port forwarding)
- Building/reading detection rules from log source + Event ID + field conditions
- Alert investigation workflow and true/false positive handling
